## 1. Fund — PASS (as reworded)

`tools/prove-solana-deposit-withdraw.ts` proves the **handoff**: the config endpoint is strictly
sandbox, the target token is `usdc_sol`, the checkout URL carries the user's own Solana address and
a `baseCurrencyAmount`, and it is HMAC-SHA256 signed with `MOONPAY_SECRET_KEY` so MoonPay will
honour it. The webhook half is separately exercised — what the app does when MoonPay reports a
completed purchase.

It does not prove arrival, and **now says so**. Completing a sandbox purchase means a human entering
card details on MoonPay's site; there is no API that makes it happen, so there is nothing to
automate and nothing to assert about a balance. The heading, the docstring and the assertion wording
were changed from "DEPOSIT" to "HANDOFF (signed checkout URL, not arrival)". The step used to read
as though the money had landed, which is a claim the file cannot support.

Reworded rather than automated, deliberately: the alternative was to leave a step that overstates
itself, and this harness exists to stop exactly that.

### Defect found and fixed: the agent's fills never reached the position book

On the first run that line read `sleeves NONE`, and the tables agreed: `positions` 0 rows,
`position_sleeves` 0 rows — while the signature was `Confirmed` on chain. `guardAndSpend` places the
swap and returns a receipt; it does not touch `positions`, and nothing on the autonomous path did
either. So an autonomous buy moved real money, wrote an audit row and sent a notification, and then
did not appear in the book at all: Holdings showed nothing, P&L counted nothing, and the sleeve
breakdown had nothing to attribute.

Fixed in `server/src/bot/autonomous.ts`: the cycle now books the fill through `applyFill`, attributed
to `agent` and to the proposal that decided it. A sale books as negative units. Both pinned by tests.

## 4. Fill — PASS, after a fix

**First run failed.** The route reverted and the fill silently degraded to the vault:

```
Program whirLbMiicVdio4qvUfM5KAg6Ct8VwpYzGff3uctyCc success
Program JUP6LkbZbjS1jKKwapdHNy74zcZ3tLUZoi5QNyVTaV4 failed: custom program error: 0x1771
...
FILL PATH   venue-vault — NOT a Jupiter swap
PROOF FAILED: Filled through 'venue-vault' ... no on-chain route executed.
```

`0x1771` is 6001, Jupiter's `SlippageToleranceExceeded`. Note the Whirlpool CPI **succeeded** — the
swap executed and then Jupiter's own output check rejected it.

Cause, measured rather than guessed: the price is a **live mainnet** quote while the fill executes
against **pool accounts cloned at an earlier slot**. They drift. At $100 of NVDAx the cloned pool
delivered `45,664,177` against a 50 bps floor of `45,678,185` — short by roughly three basis points.
So the default 50 bps sits exactly on the edge, and the gap widens the longer a fork runs. Probing
the fill directly:

```
   50 bps -> venue = venue-vault
  200 bps -> venue = jupiter-route
```

Fixed in `server/src/venues/jupiter.ts`: off mainnet only, slippage is floored at 200 bps
(`FORK_MIN_SLIPPAGE_BPS`). This is headroom for a frozen clone, not a trading decision — on mainnet
the quote and the pool *are* the same moment, 50 bps is the real tolerance, and widening it there
would mean accepting a materially worse fill than the one quoted. The file already gated route
pinning the same way.

## 8. Withdraw — PASS

**It used to sign and stop.** `recentBlockhash` was set to a freshly generated public key — random
bytes wearing a blockhash's shape — the transaction was never broadcast, and the printed "signature"
was the signature BYTES hex-encoded with a `'demo_sig'` fallback. It was unsendable by construction:
that blockhash does not exist.

It settles now. The fork is stood up for the transfer — the user is airdropped SOL to pay its own
fee, funded with USDC by the fork's own mint authority (checked, not assumed, because minting with
the wrong authority fails with `owner does not match` and reads like a bug in the transfer), and the
destination ATA is created so there is an account to receive into. Then the **user** signs and the
transaction is broadcast and confirmed.

### Blocked: the agent's selection half needs a 1inch API key

Outside Nasdaq regular hours the off-hours guard holds any symbol it cannot measure against a second
venue, and that second venue is the Base listing priced through 1inch. Without a real
`ONEINCH_API_KEY` every symbol correctly reads `hold`, so `evaluateBestSetup` returns nothing and the
selection half of step 3 cannot be demonstrated — the execution half was driven directly instead.

This is a credential, not code: nothing can be built to remove the dependency without either
inventing a reference price (which the guard exists to refuse) or dropping the second-source check
entirely. The owner supplies the key, or the demo runs during Nasdaq regular hours, when the guard
returns `normal` without needing one.
